# ADR-001 — Application architecture and technology stack

- Status: **PROPOSED — awaiting owner approval**
- Related activity: ACT-05 (depends on ACT-03)
- Date: 2026-11-12
- Decision drivers: low operational complexity, clear full-stack boundaries, testability, accessible UI, relational dependencies, few external services, Claude Code maintainability.

## Context

The product turns `Full_Stack_Governance_Workbook.xlsx` (14 activities, 8 statuses, evidence-based completion, dependencies, gates) into a web application. The data set is small (one project, tens to hundreds of records). The owner works alone today and already uses Cloudflare (legacy PWA on Cloudflare Pages, see `reference/xls-pwa/`).

## Options

| Criterion | Option A: Next.js modular monolith | Option B: Cloudflare-native modular monolith |
| --- | --- | --- |
| Deployables | One Next.js app | One Cloudflare Worker (UI + API) |
| Language | TypeScript | TypeScript |
| UI | Next.js App Router, React | React Router v7 (framework mode, SSR on Workers) |
| API | Next.js Route Handlers | Hono, versioned under `/api/v1` |
| Data | PostgreSQL + Prisma | Cloudflare D1 (SQLite) + Drizzle ORM |
| Validation | Zod | Zod |
| UI kit | Tailwind + shadcn/ui | Tailwind + shadcn/ui |
| Tests | Vitest + Playwright | Vitest (+ `@cloudflare/vitest-pool-workers`) + Playwright |
| Hosting | Vercel + managed PostgreSQL (2 vendors) | Cloudflare only (1 vendor) |
| Local dev | Needs a local PostgreSQL | Miniflare emulates D1 locally, no DB server |
| Transactions | Full interactive transactions | No interactive transactions; atomic `batch()` only |
| Trade-off | Mature ecosystem, extra vendor and DB server | Fewer integrations, edge runtime limits, SQLite dialect |

## Proposed decision

Choose **Option B** for the first release.

Domain logic lives in `src/domain/governance` as pure TypeScript with no dependency on React, React Router, Hono, Drizzle or Workers. This keeps a later move to Option A (or to PostgreSQL via Hyperdrive) limited to the adapter layer.

## Consequences

- One deployable and one vendor; local development needs no database server.
- Multi-record mutations MUST use `db.batch()` (atomic in D1). Read-then-write races are acceptable at the current single-user scale; revisit with optimistic revision checks before multi-user use.
- SQLite types: dates stored as ISO-8601 text; enums enforced by Zod and domain code, not by the database.
- Schema changes use versioned SQL migrations generated by `drizzle-kit` and applied with `wrangler d1 migrations apply`.
- The official `react-router-hono-fullstack-template` could not be downloaded in the build environment (GitHub archive download blocked, HTTP 403). The scaffold reproduces its layout from npm packages (`react-router`, `@react-router/dev`, `hono`, `@cloudflare/vite-plugin`, `wrangler`). Compare with the official template when network access allows.
- Authentication and tenant isolation must be designed before multi-user production access.

## Open decisions

- Hosting region and data residency.
- Authentication provider and user roles (OpenAuth is a candidate).
- Single-project versus multi-project MVP (schema already carries `project_id`).
- Evidence file storage (R2 candidate) and retention policy.
- Excel import: one-time (default) or recurring.
- Policy for `DONE` without evidence and for pending dependencies: flag (current default, mirrors workbook) or reject.
